# Cymbal Partner Services — synthetic SaaS for the Auth Manager demo

Three mock third-party systems in one FastAPI container, one per Google Cloud
Agent Identity **Auth Manager** credential mode, plus the OAuth2 server backing
two of them. Deployed by [`../terraform/30-partner-services/`](../terraform/30-partner-services/).

| Endpoint | Auth | Mode |
|---|---|---|
| `GET /credit-bureau/v1/score` | `X-API-Key` | API key |
| `GET /insurance/v1/quote` | Bearer, client credentials | 2LO |
| `GET /openbanking/v1/accounts` · `/transactions` · `/income` | Bearer, user consent | 3LO |
| `GET/POST /oauth/authorize`, `POST /oauth/token` | — | the mock's own OAuth2 server |

Deployed public and unauthenticated by necessity — Google's token broker calls `/oauth/token` from
outside the VPC, and a human browser has to reach `/oauth/authorize` to consent).
Every endpoint enforces its own credential; there is no unauthenticated data path.

## Why it's shaped this way

**Synthetic data keyed to the Sterlings.** Julian and Elena Sterling already
exist in the `legacy-dms` fixtures with 2023/2024 tax returns, so this composes
into the existing storyline: credit score → insurance quote → applicant links
their bank → income cross-check against returns the demo already retrieved.
`/openbanking/v1/income` returns 150,000 for Julian on purpose — it reconciles.

**Two personas with separate bank data.** The consent screen asks which persona
you are signing in as, because the mock bank has no real login. That selector is
what makes per-user isolation demonstrable rather than assertable: consent as
Julian and the resulting token *cannot* read Elena's account, through the same
agent, the same tool and the same endpoint.

**A third applicant nobody asked about.** `Marcus Webb` exists in the credit
bureau as a target for the SGP "different applicant" deny demo.

**Both redirect URIs allow-listed.** Consent can be driven by Auth Manager
(callback under `agentidentitycredentials.googleapis.com`) or by Gemini
Enterprise (`vertexaisearch.cloud.google.com/static/oauth/oauth.html`). Both are
accepted so we're not blocked whichever path GE actually uses.

## Demo beats this enables

| Beat | How to show it |
|---|---|
| Credential rotation without touching the agent | Rotate the key in the vault; next call 401s; restore |
| Machine identity vs user identity | A 2LO token on a 3LO endpoint → `403`, "needs a user-delegated token" |
| **Per-user isolation** | Julian's token on Elena's account → `403` with the reason |
| **Scope governance** | An `accounts.read`-only token on `/transactions` → `403` listing granted scopes |
| Consent refusal | Deny on the consent screen → `error=access_denied`, no code issued |

## Develop and test

```bash
python3 -m venv .venv && ./.venv/bin/pip install -r requirements.txt httpx
./.venv/bin/python test_modes.py     # 27 in-process checks, no server needed
```

`test_modes.py` covers all three modes end to end, including PKCE, forged
codes, un-allow-listed redirects, and both isolation beats. Every assertion
corresponds to a beat in the demo script.

## Deploy

```bash
./build.sh v2
cd ../terraform/30-partner-services && terraform apply -var="image_tag=v2"
```

Bump the tag rather than mutating one — the Cloud Run revision is keyed on it.

## Credentials

Generated by Terraform, never committed. These are exactly what gets vaulted in
Auth Manager, and the point of the demo is that the agent never sees them:

```bash
cd ../terraform/30-partner-services
terraform output -raw credit_bureau_api_key
terraform output -raw two_lo_client_secret
terraform output -raw three_lo_client_secret
```

Rotation is a two-step on purpose — bump the `keepers` value, apply, then update
the matching `authProvider`. The gap between those steps *is* the rotation demo.

## The header Auth Manager injects

`credentials:retrieve` on an API-key provider returns `header: "X-API-Key"`, not
the `X-GOOG-API-KEY` this app originally required — verified against the live API
on 2026-07-28. `X-API-Key` is now primary; `X-GOOG-API-KEY` remains accepted so
hand-rolled curl in the runbook still works. 2LO and 3LO providers return
`header: "Authorization: Bearer"` — a name *and* prefix, not a bare name.

## Caveats

This is a lab mock, not a security reference. Authorization codes are
self-contained JWTs rather than one-time server-side records, so a replayed code
works until it expires (300s). Client secrets are plain Cloud Run env vars.
All people, accounts and credit files are invented.
